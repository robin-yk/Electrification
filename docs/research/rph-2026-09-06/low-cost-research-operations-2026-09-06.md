# RPH 연구의 계산비·토큰 절감 운영 설계

## 결정

최소 구현은 기존 Cantera 실행기에 검증 가능한 조기 종료와 기계 생성 요약을 추가하는 것이다. 새 LLM 서비스, 다중 에이전트 조직, 대시보드부터 만들지 않는다. 큰 구조는 아래처럼 분리하되, 현재 구현된 부분과 제안을 구분한다. 이 문서는 프로젝트 운영 설계이며 위키 공통 규칙을 수정하지 않는다.

연수의 연구 질문 → 승인한 실행 카드 → Python 실행·검증 → 결과 저장·짧은 요약 → LLM 해석 → 연수의 다음 배치 승인

계산 중의 상태 확인, 수지 계산, 그래프 생성, 캐시 조회에는 LLM이 필요하지 않다. 연구 질문, 모델 가정의 타당성, 예상 밖 결과의 해석, 논문 주장은 연수와 LLM이 담당한다. 계산 결과가 자동으로 다음 대규모 계산을 승인해서는 안 된다.

## 1. 이번 실행에서 실제로 낭비된 것

1. 약 1분마다 LLM이 GitHub 상태와 브라우저 로그를 읽고 같은 진행 상황을 중계했다. 결과가 변하지 않아도 도구 출력과 대화 문맥이 늘어났다.
2. 고온 조건은 주기 경계 상태가 2–3주기에 수렴했지만 최소 20주기를 강제했다. 수치 검증용 보수적 실행이었으며 반드시 필요한 계산량은 아니었다.
3. 30분 작업 제한 때문에 실행을 나눴다. 완료 파일은 재사용했지만 중단 시점의 미완료 계산은 이어받지 못했다. 완료된 case 캐시와 적분기 내부 상태 checkpoint는 다르다.
4. 연구 논의, 코드 수정, 실행 감시, 원고·위키 작업을 긴 대화 하나가 모두 맡았다. 매번 과거 서술에서 상태를 재구성하게 됐다.

첫 두 고온 조건의 결과는 [세 조건 실행 기록](gri-aramco-three-rph-pairs-2026-09-06.md)에 있다. 세 번째 조건의 GRI는 28주기가 필요했다. 따라서 최소 주기 수를 줄이면 모든 조건이 같은 비율로 빨라진다고 말할 수 없다.

최종적으로 원래 짝비교는 12개 중 11개 계산을 완료했고, 마지막 Aramco 세분화 계산은 후속 실행의 29분 시간 제한으로 종료됐다. 완료 출력은 모두 보존했으며 추가 재실행은 하지 않았다. 이 미완료 적분은 중간 상태가 없어 복구할 수 없다. 따라서 다음 구현 우선순위는 주기 경계 상태·누적 수렴 기록의 저장과 복원이다. 복원 결과가 중단 없는 계산과 일치하는지 검증한 뒤 사용해야 한다. 현재는 구현되지 않았다.

## 2. 책임 분리

| 구성요소 | 맡는 일 | LLM 호출 |
|---|---|---|
| 실행 카드 | 질문, 조건, 모델, 검증 기준, 예산, 중단 조건 고정 | 작성·변경 판단 시 |
| 실행기 | Cantera 실행, 수렴 판정, 시간 제한, 완료 파일 저장 | 없음 |
| 검증기 | 원소수지, 전체 탄소 그룹, 시간격자, 재현성 검사 | 없음 |
| 결과 저장소 | 입력·메커니즘·해석기 해시와 결과 연결 | 없음 |
| 요약기 | 검증 결과·수율·변경된 순위·실패 항목 정리 | 없음 |
| 연구 해석 | 왜 달라졌는지, 무엇을 더 검증할지, 주장 범위 결정 | 배치 종료·실패 또는 연수의 질문 시 |

공식 OpenAI 권고도 요청 횟수를 줄이고, 정형 계산·출력에는 일반 코드·캐시·UI를 사용하는 접근을 제시한다. 여기서는 이를 연구 실행과 해석의 분리에 적용한다. [OpenAI latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

## 3. 계산량을 줄이는 순서

### 3.1 결과가 안 변하면 멈춘다

기존 해법과 시간격자를 유지하고, 조기 종료만 선택적으로 적용한다.

- 최소 3주기 이후 종료를 허용한다.
- 전체 종의 주기 경계 질량분율 최대 변화가 10⁻⁸ 미만이어야 한다.
- 전체 종의 한 주기 평균 유출 질량분율 최대 변화도 10⁻⁸ 미만이어야 한다.
- 두 기준을 3회 연속 만족해야 한다. 중간에 실패하면 연속 횟수를 0으로 되돌린다.
- 최대 주기 수는 유지하며, 미수렴은 실패로 기록한다. 마지막 값을 정상상태 수율로 사용하지 않는다.
- 결과의 수지와 시간격자 검사는 그대로 유지한다.

경계 상태만 거의 같아도 주기 적분 수율은 아직 변할 수 있어 유출량 검사를 추가했다. 이 조건도 모든 느린 모드를 증명하는 것은 아니므로 대표 조건에서 긴 계산과 비교한다. 향후 주기 2 이상 진동이 발견되면 주기 1 정상상태 가정 자체를 재검토한다.

구현은 별도 비용절감 브랜치에 있다. 기본 해석기의 기존 종료 설정은 유지하며, 저비용 설정은 선택적으로 사용한다. 세 개의 짧은 재현 계산을 20주기 저장 결과와 비교하는 검증의 상한은 5분이다. C₂H₂·C₂H₄·C₂H₆·C₆H₆·CO 및 전체 C₂·C₆ 탄소수율, CH₄ 전환율의 절대차를 각각 10⁻⁶ 이내로 요구한다. 검증 전에는 절감률을 확정하지 않는다.

2026-09-06 미국 동부시간에 [검증 run 34078455559](https://github.com/robin-yk/Electrification-Suite/actions/runs/34078455559)이 성공했다. 커밋 2efdd05. [원본 비교 결과](data/early-stop-validation-2026-09-06/validation.json)에 다음 값이 저장돼 있다.

| 조건·메커니즘 | 기존 주기 | 조기 종료 주기 | 주기 감소 | 기존/조기 종료 wall time (s) |
|---|---:|---:|---:|---:|
| 6300012 GRI | 20 | 5 | 75% | 17.48 / 4.75 |
| 6300012 Aramco | 20 | 5 | 75% | 348.08 / 90.99 |
| 6000015 Aramco | 20 | 6 | 70% | 325.51 / 102.25 |

검사한 탄소수율의 최대 절대차는 약 1.55×10⁻¹¹이었다. 실행시간은 서로 다른 runner에서 측정했으므로 배속은 참고값이다. 주기 감소와 수율 일치가 직접 확인된 근거다. 현재 진행 중이던 세 조건의 원본 계산은 변경하지 않았다. 새 고온 조건의 저비용 실행에서 이 종료 정책을 사용할 수 있으나, 새로운 물리 구간의 검증을 생략할 근거는 아니다.

### 3.2 이미 한 계산은 재사용한다

현재 세 조건 실행기는 완료 파일을 재사용한다. 향후 공통 저장소에서는 아래 항목의 정확한 해시를 캐시 키로 사용한다.

- 메커니즘 원본과 해석기 버전
- 반응기·유량·온도 결합 가정
- 조성, 압력, 체류시간, 실제 표본화한 온도 파형
- 시간격자, 적분 오차 허용치, 종료 정책

화면에 표시할 때 반올림한 값으로 캐시 키를 만들지 않는다. 입력은 같아도 검증 기준이 달라졌다면 자동 승인하지 않는다. 실패·미완료·검증 통과 상태를 구분한다. 캐시 키 함수는 구현했지만, 모든 기존 연구 계산을 통합하는 저장소와 작업 잠금은 아직 제안 단계다.

### 3.3 시간격자는 질문에 필요한 수준까지만

첫 pilot에서는 모든 조건의 기본·세분화 격자를 비교한다. 검증된 구간에서 이후 screening 격자를 정하되, 새로운 파형·극단 조건·최적점 후보·순위 차이가 작은 조건은 다시 세분화한다. 높은 순위를 얻기 위해 격자 기준을 완화하지 않는다.

후보 두 개의 수율 차이가 수치 오차와 비슷하면 순위를 확정하지 않는다. 먼저 그 두 개만 더 정밀하게 계산한다. 수렴하지 않는 결과를 surrogate 학습에 넣지 않는다.

### 3.4 메커니즘 크기와 필요한 질문을 맞춘다

현재 설정은 GRI에 dense, Aramco에 희소 전처리 해법이다. 이것은 이미 적용됐다. GRI는 초기 탐색·코드 검사·저비용 보조 변수로 사용할 수 있지만, 이번 두 조건에서는 Aramco와 수율 순위가 달라졌다. GRI 순위만으로 Aramco 후보를 탈락시키는 규칙은 아직 정당화되지 않았다.

반응 삭제·메커니즘 축약·가스 에너지방정식 생략 등 모델을 바꾸는 절감은 단순 가속과 구분한다. 새 모델이면 별도 검증이 필요하다. 가스상 C₆를 soot로 대체해서 집계하지 않는다.

## 4. 토큰을 줄이는 실제 운영 방식

### 4.1 실행 중 LLM 호출을 없앤다

GitHub Actions 또는 일반 실행 코드가 시작부터 종료까지 진행한다. 상태 감시는 LLM을 깨우는 분 단위 반복 대화가 아니라 작업 상태/API 또는 완료 이벤트로 처리한다. 사용자가 중간 상태를 요청하면 완료 개수·현재 단계·예산만 한 번 읽는다. 브라우저 전체 DOM과 전체 로그는 오류 진단이 필요한 때만 사용한다.

완료 알림을 GitHub 자체 알림으로 받을지, 별도 제품 자동화로 받을지는 실제 구성 단계에서 정한다. 이 문서만으로 알림 설정이나 새 반복 자동화를 설치한 것은 아니다. LLM이 주기적으로 깨어나는 heartbeat 역시 호출 비용이 있으므로 무조건 무토큰 감시라고 부르지 않는다.

### 4.2 상태는 대화가 아니라 파일이 보유한다

한 프로젝트에 아래 네 역할만 유지한다. 기존 파일이 있으면 재사용한다.

| 파일 역할 | 필수 내용 | 읽는 시점 |
|---|---|---|
| 실행 카드 | 질문·입력·가정·검증 기준·승인된 예산 | 시작·범위 변경 |
| manifest/status | 커밋·해시·실행 ID·완료/실패 상태 | 자동 실행·수집 |
| brief | 변경된 수치, 검증 통과 여부, 실패 원인 코드, 원본 경로 | LLM이 다시 판단할 때 |
| 연구 결정 기록 | 결론, 반례, 미확인 가정, 다음 승인 사항 | 연구 방향 논의 |

raw trajectory와 전체 로그는 파일로 남기고 프롬프트에 자동 첨부하지 않는다. 요약만 보고 판단할 수 없을 때 해당 case의 원본을 선택해서 읽는다. 위키 필수 규칙을 생략하는 방식으로 토큰을 줄이지 않는다.

### 4.3 문맥 예산은 측정 가능한 목표로 둔다

제안 목표는 배치당 시작 판단 1회와 종료 해석 1회, 오류가 있을 때만 추가 진단이다. 초기 brief는 수천 문자 이내로 제한하고, 원본 데이터를 찾을 수 있는 경로와 검증 실패를 생략하지 않는다. 추가 진단은 한 번에 한 실패 유형만 다룬다.

현재 `run_digest.py`는 정제된 JSON만 출력하고 6,000자를 넘으면 개수와 원본 경로만 반환한다. 이는 실제 토큰 수 제한이 아니라 출력 길이 제한이다. Codex 전체 문맥·내부 추론 토큰을 이 스크립트가 제한하는 것은 아니다. 정확한 토큰 예산 집행은 해당 제품이 제공하는 사용량/예산 기능 또는 향후 API 사용량 계측과 별도로 연결해야 한다.

단순 로그 요약에 작은 LLM을 추가하는 것보다 먼저 일반 코드로 대체한다. 모델별 분업은 실제 평가로 이득이 확인될 때 선택하며, 이 문서에서 새 모델이나 유료 API 호출을 설정하지 않는다.

## 5. 예산과 중단 규칙

이번 연구 계산의 승인 한도는 총 60분이다. 별도 조기 종료 검증을 포함한 계산 단계의 상한을 그 안에 둔다. 작업 설치·업로드·코드 테스트 시간과 화학 적분 시간을 분리해서 기록한다.

향후 배치에는 case 수, 동시 worker 수, CPU 시간, 벽시계 시간, 재시도 수, LLM 호출 수를 각각 둔다. 여러 worker를 사용하면 벽시계 시간이 짧아져도 총 CPU 비용은 줄지 않을 수 있다. 시작 전에 남은 예산을 예약하고, 실제 사용량을 반영해 반환하는 방식이 필요하다. 이 공통 예산 관리자는 아직 구현되지 않았다.

수지 실패, 미수렴, 격자 실패는 물리적 발견으로 해석하기 전에 격리한다. 같은 실패를 자동으로 무한 재시도하지 않는다. 네트워크 등 일시적 실패의 제한 재시도와 과학적 실패의 재계산을 구분한다. 예산 상향과 새로운 조건 축은 연수가 승인한다.

## 6. 연구 확장의 승인 단계

1. 현재 세 조건에서 메커니즘 차이와 수치 신뢰성을 확인한다.
2. 조기 종료 검증으로 조건별 필요 주기와 비용을 측정한다.
3. 대표성을 설명할 수 있는 작은 설계 배치를 정한다. 평균 온도·진폭·주기·duty·체류시간의 독립성과 물리적 실현 가능성을 먼저 확인한다.
4. 그 결과로 surrogate의 학습곡선과 불확실성을 확인한다. GP/active learning은 이 단계 이후의 제안이며 현재 실행하지 않는다.
5. 다음 배치는 예상 개선량 또는 불확실성 감소를 계산비와 함께 평가해 승인한다. 최적점 후보는 직접 Aramco 계산과 별도 수치 검증으로 확인한다.
